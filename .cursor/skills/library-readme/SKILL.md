# ライブラリ README

出荷済みの挙動だけを書く。契約の正本が別にあれば、README は判断用で、未実装の API は書かない。このリポジトリの README は日本語。文は `。` で終えてよい。

参照した README: FluentValidation（リポジトリの一文は strongly-typed な検証）、R3、Polly、Spectre.Console、Humanizer、Dapper、Refit、Serilog、FluentAssertions、BenchmarkDotNet。

## 構成

この順。空の節は置かない。

1. **一文**。何をするライブラリか。誰向けかを同じ文に含めてよい。実装の固有名詞（一時ファイル名、内部フォルダ）はまだ出さない
2. **最小のコード**。インストールが無ければ「どう参照するか」を 1 文。コードはコピペでき、その言語のいちばん短い成功パスだけ
3. **そのコードで何が起きるか**。2〜4 文。戻り値の意味は表にしてよい
4. **できないこと**。機能一覧より前。仮定しやすい失敗を先に潰す
5. **操作の一覧**。動詞と 1 行。オーバーロードは書かない。詳細は後続の節か正本へ
6. **特徴が分かる例**。成功パスでは見えない振る舞いを、コード 1 つで示す
7. **操作の説明**。一覧のあと、利用者がコードを読まずに使える手順を書く。このリポジトリは利用者向けの別ページが無い。流れが分岐するものは図にする。同じ事実を表と散文で繰り返さない
8. **比べる**。読者が既に知っている代替が本当にあるときだけ。先に「有利なとき / 不利なとき」を書き、表は観点を揃える
9. **正本へのリンク**、ビルド、ライセンス。貢献の手順は CONTRIBUTING に任せ、README に複製しない

## コード例

- 最初の例は 15 行以内を目安にする
- 2 つ目の例は、このライブラリでないと分かりにくいことだけを見せる
- 例外名とメッセージを書くときは、実装の文字列と一致させる
- サンプルのパスと API 名は実在するものだけ

## 書かない

- バッジ、スポンサー、行動規範を先頭に置かない
- 未公開のパッケージを `dotnet add package` で案内しない
- 正本（設計）に無い挙動を足さない
- プロセスの進捗（Issue 番号、Phase）を本文の中心にしない。公開状態が利用者の入手方法を変えるときだけ、短く書く
